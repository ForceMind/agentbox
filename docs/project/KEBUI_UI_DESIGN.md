# Kebui UI 与交互设计方向

日期：2026-10-07。状态：**设计方向与验收要求；不是已实现界面，也不是最终视觉定稿。**

本文件落实 Owner 的补充要求：UI 要更好地设计，并参考此前提供的项目。
品牌继续使用 **Kebui / 科布**；不重新命名，不更改现有服务、协议或仓库标识。

入口：[品牌规范](KEBUI_BRAND.md) · [产品计划](KEBUI_PRODUCT_PLAN.md) ·
[UI 分阶段交付计划](KEBUI_UI_DELIVERY_PLAN.md)。

## 1. 设计结论

**像通讯工具一样容易开始，像工作台一样能检查过程与结果。**

不是给管理后台换一个 Logo，也不是把终端输出排成聊天气泡。
用户应能清楚回答：我在处理哪个项目、谁在执行、现在卡在哪里、需要我做什么、结果在哪里。

Conversation-first 是交互入口；Project-bound 是工作与权限边界，两者不矛盾。
第一阶段进入具体工作前仍显式确认 Project 和 Agent，不假装已实现自动选择。

Kebui 可以是默认对话身份，但 Claude Code、Codex 等实际执行者必须可见。
普通用户不必先理解 Harness、Provider、Runtime、Session；高级用户仍能查看真实状态。

## 3. 信息架构

### 首期结构化会话具备准入条件后的用户入口

| 层级 | 用户看到的内容 | 不应强迫用户先理解的内容 |
| --- | --- | --- |
| 工作 / 对话 | 最近工作、需要回复、进行中的对话、新建工作 | Runtime 进程、Provider 配置列表 |
| 项目 | 正式项目、最近工作、关联 Agent、已获准的 Changes | 任意主机目录选择器 |
| 工作详情 | 对话、阶段、需要确认的事项、可检查的结果 | 没有解释的原始事件流 |
| 设置 | 外观、语言、账户、Agent 与运行环境的分组入口 | 把所有系统字段铺在首页 |
| 高级检查 | CLI、诊断、精确连接/权限状态 | 永久隐藏运行事实 |

Tasks、Artifacts、Memory、团队空间只有对应合同与能力可用后才进入正式导航。
在独立原型中可预演，但必须有“设计演示 / 规划功能”标记；生产不得摆放假可用入口。

### 当前 rc31 的处理

继续既有路由和页面呈现迁移，不立即把 Dashboard 换成未实现的 Chats。
当前 Job 仍称后台操作，不能改名为 AI Task 后声称任务系统已完成。
现有 WAW/终端仍可作为工作入口，不因未来 Chat 设计而移除已可用操作。

## 4. 桌面布局

建议在 1440px 设计画板上采用三个有明确职责的区域，而不是三列信息卡堆叠：

```text
左侧：工作导航与列表     中间：当前工作/对话       右侧：按需打开的检查面板
项目、最近会话          项目 + Agent + 状态        Changes / 结果 / 执行详情
待回复、进行中          用户请求、执行摘要          不自动读取受限正文
新建工作               阶段/确认/结果卡片          返回原对话位置
设置与高级入口          固定但不遮挡内容的输入区   CLI 为独立高级查看
```

建议起点：左侧约 240–280px，右侧约 320–400px，中间保留可读宽度；不是固定像素合同。
屏幕变窄时先收起检查面板，再压缩导航；不可把三栏硬挤到笔记本或手机上。
1024px 优先两栏与可关闭检查面板，768px 优先单个工作内容区域。
最终断点根据真实内容、200% 缩放和页面几何检查调整，不依据设备名称猜测。

上下文条展示项目、选中 Agent、运行环境摘要和真实状态。高级身份信息可展开，
但批准、停止或跨 Agent 操作时必须展示明确目标，不能只剩装饰性的绿点。

## 5. 手机布局

手机不是缩小的 IDE，而是远程工作的沟通、确认与检查入口。

会话列表采用头像/身份、工作标题、最近进展、时间和状态的纵向行结构。
“未读”“等你回复”“待确认”“执行中”应可区分，不复用同一个红点表示四种含义。

会话详情只显示一个主区域：对话为默认，检查结果通过明确按钮进入全屏详情或底部面板。
返回后保留滚动位置与同一作用域内允许保留的草稿；切换账户/项目则按安全合同清除。

设计必须覆盖：

- 360px 与 390px 的长中文/英文消息、长项目名和错误提示；
- 键盘弹出、输入法组合、safe area、横竖屏与输入区不遮挡内容；
- 查看 diff 后返回原消息；
- 断线、后台返回、重新读取状态，绝不自动补发旧请求；
- 明确区分“退出查看”“中断当前轮次”“取消任务”“停止运行”；
- 所有重要操作有可见按钮，不依赖只有熟练用户知道的手势。

原型中的触摸区域目标至少 44px；物理 Android/iOS 验收不能由 viewport 截图替代。

## 6. 视觉设计语言

方向：**轻、清楚、有人格，但不玩具化；专业，但不做运维面板。**

沿用当前暖白/墨色作为可回退工作基线；现有琥珀点缀仅为实施假设，不等于 Owner
已经确认 Kebui 品牌色。后续用实际对比稿定主强调色，不套用其他项目的品牌规则。

| 项目 | 设计要求 |
| --- | --- |
| 层级 | 用字体、间距、区域背景区分主次；避免每段文字都包卡片 |
| 字体 | 正文以可读性为先，中文系统字体有回退；等宽字体只用于代码和标识 |
| 标题 | 应用内标题克制，不把官网营销大标题搬进每个页面 |
| 间距 | 建立统一 spacing tokens；密度随工作内容调整，不随页面作者随意变化 |
| 圆角 | 对话、输入区、卡片使用同一家族；表格/代码区保留精确对齐 |
| 图标 | 同一描边、尺寸与对齐；关键动作带文字；不混用大量 emoji |
| 身份 | Kebui 有自己的头像/标记；Agent 类型、实例/会话与人类身份有清楚区别 |
| 色彩 | 品牌强调、成功、警告、错误分开；状态同时有图标和文字 |
| 动效 | 只帮助理解展开、切换和状态改变；尊重 reduced motion，无永久大面积动画 |
| 暗色 | 独立检查层次与对比，不机械反色；保留终端 ANSI 颜色语义 |

不照搬 Cromma 的壁纸或第三方吉祥物；不使用金字塔/法老装饰当作 Kebui 的默认皮肤。
Logo、色彩和吉祥物仍需真实视觉稿，本文不能替代最终资产。

## 7. 核心组件与行为

### 7.1 ConversationRow

展示工作标题、项目、实际参与 Agent、最后进展与需用户注意的状态。
排序规则可解释；新消息不能让用户正在点击的列表项突然移位。
搜索应说明覆盖范围；没有跨项目检索能力时不得显示“搜索所有工作”。

### 7.2 ContextBar 与 AgentPicker

K2 显式选择 Project 和已支持 Agent；不同选择不代表共享上下文或权限。
K5 才允许策略选择，并展示选中者、原因与覆盖入口。
正在执行时切换 Agent 必须走明确的新轮次/交接合同，不仅更换头像与标签。

### 7.3 Composer

可见项目与执行者，输入、提交中、失败、等待恢复各有独立状态。
默认 Enter 换行，Ctrl/Cmd+Enter 提交；中文 IME 组合事件不得发送。
附件、语音、命令菜单只在获准能力存在时开放。
发送后区分“已接受”与“已开始执行”，失败时不伪造回执；重试不产生重复工作。

### 7.4 WorkStageCard

展示已发生的阶段、当前执行者、更新时间和阻断原因。
不制造百分比、预计完成时间或虚假的“正在思考”。
任务成功须由可信结果判定，不能用 CLI 退出、Job 完成或连接在线替代。

### 7.5 ApprovalCard

审批是可操作卡片，不是一句散落在长对话里的“是否继续”。
必须展示操作目标、范围、后果、申请者、有效期及拒绝/取消入口。
确认绑定当前 owner、Project、request/revision；状态过期、目标改变或切换账户后失效。
“批准当前操作”不隐含“永远允许”，自然语言肯定句不能自行扩权。

### 7.6 ResultCard 与 Inspector

结果有清楚类型：文档、代码变化、验证结果、已有 PR 链接等。
数量和成功结论来自实际证据，缺失数据明确写未知。
文件/补丁正文仍需各自的准入与显式读取，不因卡片可见而后台预取。
不直接执行仓库 HTML、Markdown 脚本或未经隔离的预览内容。

### 7.7 RecoveryBanner

区分正在连接、连接断开、权限失效、服务不可用、Agent 退出和执行结果未知。
恢复过程重新核对身份与当前状态，不重放消息、批准、Git 写入或停止操作。
终端操作中 Detach 不是 Stop；停止成功必须保留原 exact Stop 证据要求。

## 9. 三条必须做成完整原型的用户旅程

### A：交代工作并检查结果

选择 Project 和 Agent → 输入请求 → 已接受/执行中 → 查看阶段 →
打开 Changes/结果 → 返回同一对话。没有已实现 Chat 时明确为独立演示。

### B：等待用户确认

会话列表看到“待确认” → 打开有明确范围的审批卡 → 确认或拒绝 →
显示实际提交/回读状态 → 过期或网络失败后不自动重试。

### C：手机回来继续

离开页面/断线 → 手机重新进入 → 显示重新核验而非假完成 →
恢复已确认的工作状态 → 查看结果或明确停止。未知结果不能推断为成功。

每条旅程同时覆盖成功、失败和中断，不只给一张漂亮首页。

## 10. 设计与实现验收

交付顺序：参考板 → 信息架构/流程 → 核心高保真页面 → 可交互原型 →
现有组件映射 → 分批生产实现 → 浏览器/像素/真实设备资格。

设计评审至少交付六组核心画面：工作/会话首页、对话执行、待审批、结果检查、
Agent/环境详情、手机恢复。每组必须有桌面与手机，并覆盖浅/深主题的代表性状态。
完整页面清单里的其余页面也须进入交互原型和状态清单，不能用六张图冒充全量完成。

每个交付包应记录文件路径、设计版本、参考来源、样本标记、实际打开/点击的路径、
已知问题与下一步；Owner 能直接打开 HTML/看到图片，而不是只能阅读完成声明。

生产验收必须同时检查：

- 普通用户能找到当前工作、执行者、阻断原因、下一步与结果；
- 正式数据和合成演示有明确边界，不解析 TUI 字符串伪造工具事件；
- 360/390/768/1024/1440px，zh-CN/English，浅/深主题，长文本与大字体；
- 键盘可到达、焦点恢复、标签、可读对比、不能仅靠颜色传达状态；
- drawer/modal 不遮挡关键确认，Back/Escape 不错误取消已提交操作；
- 新旧 owner、过期结果、迟到回包、离线恢复与无隐藏正文读取；
- exact-head CI 与该版本实际截图；图片审查覆盖范围如实记录；
- 物理客户端/真实 CLI/目标 host 另列证据，软件 UI 通过不能替代。

主实施者检查只称自查，不称独立审查。没有运行浏览器就不能声称完成像素验收。
