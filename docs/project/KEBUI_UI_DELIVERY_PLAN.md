按钮应真实演示局部状态变化；尚无能力的按钮解释原因，不用空按钮假装完成。

## 7. U3 首个聊天工作台的退出条件

实施前先确认 S03/WEV 对结构化会话、正文通道、历史与审批的合同，不能把普通
API 升级成任意命令入口。第一版只显式调用真正支持的 Agent；自动选择在 K5。

成功路径：Project → Agent → 已接受的 turn → 执行进展 → 结果/Changes 检查 → 返回。
恢复路径：断线 → 重新确认身份/任务 → 回读实际状态；无暗中重试或重复写入。
控制路径：等待用户 → 明确范围的审批/拒绝；当前轮次中断和 exact Stop 分开。

完成必须有真实接口与结构化事件来源、必要回归、桌面/手机操作和该 head 的
浏览器截图。无真实 target/CLI 证据时仍只称软件资格，不宣布部署可用。

## 8. 每批交付协议

1. 回读 main、工作分支、PR、差异及 exact-head CI，保护并发修改。
2. 记录本批页面与能力边界；设计示例和真实产品分开。
3. 先交付可看的画面/可操作原型，再按现有合同做有限实现。
4. 验证输入、状态、权限、失败/恢复、可访问性和浅/深主题；不为通过放宽断言。
5. 更新来源、状态、问题和产出路径，正常提交与推送。
6. 必要 CI 全终态后再按当前授权正常合并并回读；没有新 head 证据不借旧六绿。

日常迭代不增加逐页人工审批门槛。视觉可以根据反馈继续改，但不能宣称未确认的
颜色/Logo 是最终品牌定稿，也不能把主实施者自查称为独立审查。

## 9. 不可省略的交付报告字段

每批说明：哪些文件变了、哪个页面可打开、哪些交互实际验证、当前 commit/PR、
CI 的实际状态、哪些仅是样本，以及下一项有界工作。

最终“完整 UI 已完成”仅在页面清单、状态清单和实际验证都闭合时使用；
“品牌文件已推送”不等于“UI 已重做”，“截图好看”也不等于“真实工作能完成”。
